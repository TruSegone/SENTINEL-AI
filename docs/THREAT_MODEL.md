# Threat model and deployment limits

Trust boundaries: browser to API; API to database; untrusted event payloads to storage/detection; bounded incident evidence to investigation output; analyst approval to simulation adapter. Event strings are length-limited, JSON blobs bounded, IP/port values validated, writes require the demo token, graph/batch/query results are bounded, and response targets are restricted to synthetic address spaces or `*.test`. The simulation adapter registry has no shell, firewall, account-provider, or host-management implementation.

Threats addressed in this demo: duplicate event IDs, invalid event fields, prompt injection in records (no external LLM call), invalid evidence citations, approval replay after payload change (hash binding and expiry), unapproved response execution, arbitrary remediation, and oversized request fields. Audit entries are append-only at the application layer.

Production gaps: demo header auth is not identity verification; no tenant isolation or object ownership policy; no production rate limiter; CORS must be narrowed; TLS/reverse proxy and secret manager are external; SQLite does not support robust concurrent workers; database-level audit immutability is absent; Redis buffering/backpressure and dead-letter queue are not wired; OTel spans and detailed latency metrics are not yet implemented; external AI provider integration is absent; model metadata is cold-start unless separately trained. The new-source-IP rule is a simple stored-event comparison, not a mature baseline. Cross-host correlation is a bounded same-source temporal association, not causal analysis. Deploy only with synthetic data until these controls are designed and tested. Run containers as non-root and pin base image digests in a production pipeline.
